# 回放录制 APP × Sodayo 云盘上传对接 —— 动工方案

> 依据材料：
> 1. `highlight-recorder-可行性分析报告.md`（对 https://github.com/owen88ob/highlight-recorder 的源码级评估）
> 2. `Sodayo-Android-APK-Docs-Fixed/Sodayo-Android-Drive-Integration-Spec.md`（对接协议草案 Draft v0.1）
> 3. `Sodayo-Android-APK-Docs-Fixed/Sodayo-Android-Instant-Replay-Development-Plan.md`（开发建议计划书 v1.0）
> 4. Cloudreve V4 官方上传协议文档（https://docs.cloudreve.org/zh/api/upload ，已核实）
>
> 结论速览：**方案可行。上传协议复用 Cloudreve V4 原生三步协议（现成、服务端纯上传零开发）；难点集中在设备授权（Drive 侧待建）。APK 侧可立即动工，总工作量约 5–8 个工作日出可联调版本。**

---

## 一、可行性判断

### 1.1 上传协议本身是现成的

Sodayo SH Drive 是 **Cloudreve V4 的 fork**，文件上传直接走 Cloudreve 原生三步协议（已对照官方文档核实）：

1. **创建上传会话** → 服务端返回 `session_id`、`chunk_size`、`upload_urls`、`credential`、过期时间和存储策略类型；
2. **分片上传** → 按服务端返回的 `chunk_size` 分片，路径因存储策略而异：
   - 本机/从机存储：走 Cloudreve 的 Upload file chunk API，带 `credential` 头；
   - S3 类对象存储：走预签名 URL PUT；
3. **完成** → 本机/从机存储最后一片传完自动完成；S3 类需要显式 Complete 回调。

**含义：服务端"纯上传"这条路零新增开发**。之前可行性报告中"WebDAV / MinIO / 自写接收端三选一"的设想被 Sodayo 对接文档正式取代——不要自建任何接收端，直接复用 Cloudreve 原生协议。服务端复杂度集中在**认证**（见下）。

### 1.2 关键风险：对接协议是草案，设备授权还没实现

Sodayo 对接文档反复强调（这是读文档最重要的结论）：

- 所有 `/sodayo/ingest/`、`/sodayo/devices/pair` 路径都是**拟议接口，未在服务端实现**。原文："绝对不要直接把拟议接口示例当成已可调用的真实接口"。
- 设备绑定、专用上传 Token：**未实现/待开发**；`client_upload_id` 幂等、上传事件元数据：**协议待定/需服务端配合**。
- 正式 Drive 根地址 `https://sh.sodayo.net:8621` **尚未确认**为可用的 V4 APK 联调环境。

所以"云盘对接"的真实状态是：**上传协议有了，但"APK 用什么身份登录"还没有**。设备授权（浏览器配对、可撤销设备 Token）是整个方案的认证基石，目前是纸面设计。

### 1.3 判断：可行，前提是把认证依赖解耦

APK 侧可立即动工，架构上做一个关键设计——**把"认证方式"和"上传协议"分离**：

```
UploadScheduler (WorkManager 唯一队列)
      │
UploadTaskRepository (Room 持久化, 幂等键, 状态机)
      │
CloudreveV4Uploader  ←── 按官方协议写，稳定不变
      │
CredentialProvider (接口) ←── 唯一会换的部件
   ├─ 开发/联调期：测试账号 Token（自建测试实例）
   └─ 正式版：Drive 侧交付的设备 Token（Keystore 加密保存）
```

开发期用自建的 **vanilla Cloudreve V4 测试实例**（开源，随时可部署）+ 测试账号 Token 跑通全链路；等 Drive 侧设备授权接口交付后，只换 `CredentialProvider` 的实现，协议层一行不动。这正是 Spec §13 建议的"双方并行"路径。

## 二、必须遵守的对接规范（Sodayo 文档硬性要求）

实现时逐条落实：

| 要求 | 出处 | 落地方式 |
|---|---|---|
| **先落盘、再入库、后入队**：文件写成功 → Room 事务 → WorkManager 入队，顺序不可倒 | Spec §6 | 在 `ClipWriter.write()` 成功回调里依次做三步；`savedEvents` Flow 只用于 UI 提示 |
| **`client_upload_id` 幂等键**：任务创建时生成 UUID，重试永不变化 | Spec §2.4 | 存 Room，作为服务端幂等和本地任务主键 |
| **SHA-256 客户端预计算，服务端复核** | Spec §6/§7 | ContentResolver 流式哈希，后台算，不占内存 |
| **客户端身份字段不可信**：不传 `uploader_user_id` 等越权字段 | Spec §2.1 | 请求体只带文件元数据，身份由 Token 推导 |
| **App 被杀后队列可重建**：不依赖内存 Flow | Spec §6 | Room 是唯一事实来源，启动时扫表重建 |
| **错误码语义**：401 暂停队列、403 停止重试、409 查既有结果、413/配额不足停止重试、429 尊重 Retry-After、5xx 可重试 | Spec §7 | Worker 里按状态码分支处理 |
| **HTTPS only、不写死 localhost、不内置任何密码/管理密钥** | Spec §9 | base URL 配置只允许 https 且校验为公网 host（拒绝 localhost/环回/私网/保留地址）；发行包内只有设备凭据交换流程，无共享密钥；生产禁用 Mock CA/跳过 TLS 校验 |
| **上传成功默认保留本地原件** | 计划书 §2.4 | 删除仅作可选设置，默认关 |
| **不让 APK 自动绑定处罚记录** | Spec §8 | 上传到收件目录即止，OA 关联由员工在网页 `/game-records` 完成 |
| **默认单上传并发 1**，分片按服务端 `chunk_size`；Wi-Fi/蜂窝策略可配置 | Spec §7 | WorkManager 网络约束 + 设置页开关，默认仅 Wi-Fi |

## 三、动工步骤（五步走）

### 第一步（立即，发出去就能等回复）：向 Drive 团队发 Spec §11 清单

8 个必须由对方提供的东西，其中 4 个直接决定 APK 怎么写：

1. HTTPS 联调环境地址（staging，非拟议正式域名）；
2. **fork 实际使用的存储策略**（本机存储还是 S3 类？——决定分片上传走 relay 还是预签名 URL，两者代码路径完全不同）；
3. 设备授权接口的实施进度和时间表；
4. fork 相对上游的接口改动核对表（防协议漂移）。

其余 4 项：上传目标目录的 folder ID 获取规则、上传完成后 file_id 的确切返回协议、文件类型/大小限制与幂等语义、测试账号与密钥回收方式。

### 第二步（立即可做，1 天）：自建 Cloudreve V4 测试实例

找台 VPS 或本机 Docker 部署原版 Cloudreve V4，配一个测试存储策略和测试账号。这给了 APK 开发一个**今天就能打的真接口**，完全不被 fork 的进度阻塞。

### 第三步（1 天）：fork highlight-recorder，M0 设备验证

clone、编译（JDK 17+，`./gradlew assembleDebug`）、真机跑通录屏保存。**重点确认**：`ClipWriter` 产出的 MediaStore Uri 在设备重启后仍可读——需要 `takePersistableUriPermission`，否则 Room 里存的 Uri 会失效。这是原 App 和上传模块之间唯一需要小心的接缝。

### 第四步（3–5 天）：M2 上传模块（APK 侧主体工作）

按优先级：

1. **Room `UploadTask` 表**：字段照抄 Spec §6——`clientUploadId`（UUID 主键）、`contentUri`、`fileName`/`mimeType`/`sizeBytes`、`sha256`、`recordedAt`/`durationMs`、`state`（QUEUED/UPLOADING/RETRY_WAIT/DONE/FAILED）、`cloudreveSessionId`、`uploadedParts`、`serverFileId`、`retryCount`/`nextRetryAt`/`lastError`；
2. **WorkManager 前台 Worker**：大文件上传必须 `setForeground()`（100–500MB 在普通后台 Worker 里会被系统掐掉，计划书 §3.4 已提醒；API 34+ 需要 `dataSync` 前台服务类型和用户可见通知）；
3. **OkHttp 流式分片上传**：实现 Cloudreve 三步协议；先做 relay 分片路径，S3 预签名路径等第一步确认存储策略后补；
4. **设置页**：上传开关、服务器地址（https 校验）、仅 Wi-Fi、成功后是否删本地；
5. **视频库上传状态角标**：排队 / 上传中 / 失败 / 完成，管理层一眼看出谁没传。

### 第五步（Drive 侧交付后，2–4 天）：M3 联调

接入真实设备授权，跑 Spec §10 的 I01–I14 验收清单，重点用例：

- **I04** 断网重启再续传：同一任务无重复文件，原件仍在本地；
- **I05** 50 GiB 配额真实生效，超额有明确错误状态；
- **I10** 设备撤销/用户冻结后，后续上传立即拒绝；
- **I12** 错误格式与伪造用户 ID 被服务端拒绝。

测试结果按文档要求以 `REAL PASS` 口径出具，不用 Mock 充数。

### 明确不做（文档已拍板延期）

OA 自动绑定处罚记录、自动创建处罚记录、图片浏览器、公开分享、PC 录制端（二期独立项目，届时走同一上传协议）。

## 四、遗留风险一览

| 风险 | 影响 | 对策 |
|---|---|---|
| 设备授权接口交付时间不可控 | 正式版无法安全登录 | `CredentialProvider` 抽象 + 自建实例开发；把 Spec §13 的"三个最小契约"（①可撤销上传身份 ②原生会话上传得 file_id ③上传者可信归属）作为对 Drive 团队的最低要求 |
| 存储策略未知 | 分片路径写错返工 | 自建实例先做 relay 路径；S3 路径等确认后补 |
| fork 接口与上游漂移 | 按官方文档写的客户端联调失败 | 第一步就要 fork 的接口核对表；客户端字段解析宽容化 |
| WorkManager 长任务配额（Android 16+） | 大文件上传中途被系统限制 | 前台 Worker + 通知；评估超大文件走用户发起的传输 |
| 50 GiB 配额是否已生效未核查 | 上传超额时行为不明 | 联调按 I05 用例实测，超 quota 必须收到明确错误 |
| GPL-3.0（highlight-recorder 协议） | 修改后分发 APK 需提供源码 | fork 放 GitHub（私有仓库对协管开放访问即可），改动尽量外挂式，少碰 capture/buffer 核心 |

## 五、与原可行性报告的方案差异（重要）

1. **服务端方案已定**：原报告建议"WebDAV / MinIO / 自写接收端三选一"；Sodayo 文档已拍板——**复用 Cloudreve V4 原生上传会话，不自建任何接收端**。
2. **新增硬性要求**（原报告没有的）：Room 持久化先于入队、`client_upload_id` 幂等键、服务端推导上传者身份（客户端不传 user_id）、设备可撤销、上传者标记由服务端写入。
3. **录制端不需要从零开发**：highlight-recorder 已覆盖开发计划书 M1（循环缓冲、一键保存）的全部核心，直接 fork 改造，M1 的 3–5 天工期基本省掉。
