# highlight-recorder 作为 MC 服务器协管取证工具 —— 可行性分析报告

> 分析对象：https://github.com/owen88ob/highlight-recorder （v1.2.3，分析日期 2026-10-10）
> 结论速览：**两个需求均可行**。需求一几乎开箱即用；需求二是中等工程量的二开，接入点干净。

---

## 0. 背景与需求

一个 MC 服务器（基岩版，协管使用安卓设备巡查）计划：

- **需求一**：协管巡查时全程开着录屏软件做「即时回放」，发现违规玩家当场一键保存刚刚的画面，避免"看到违规才开始录、错过时机"的问题。
- **需求二**：为该软件增加上传云端功能——保存后自动上传到自建的云盘，实现取证上传流程自动化，并防止协管因各种原因不上传录像。

---

## 1. 项目分析：highlight-recorder 是什么

**Android 8.0+（minSdk 26 / targetSdk 35）的「游戏高光回录」App**，Kotlin + Jetpack Compose 编写，GPL-3.0 协议，作者仍在活跃维护。原理等同于 NVIDIA ShadowPlay 的即时回放。

### 1.1 核心机制

- **环形缓冲循环录屏**：`MediaProjection + VirtualDisplay → MediaCodec 硬件编码（H.264/H.265）`。编码后数据按关键帧切成 1 秒分片，内存中只保留最近 N+2 秒（N 可配置 15–300 秒），旧分片自动丢弃。全程零原始帧拷贝，长时间挂机开销可控。
- **一键保存前 N 秒**：悬浮球单击（或通知栏按钮）触发，从 IDR 关键帧边界拼接分片成 MP4，写入系统相册 `Movies/高光回录/`。**录制不中断**，几秒出结果；PTS 做了重定基，播放速度正常。
- **音频**：内录游戏声音（AudioPlaybackCapture，Android 10+）/ 麦克风 / 混音 / 静音四种模式；被系统采集策略拒绝时优雅降级，不崩溃。
- **设置项**：回退时长 15–300 秒、分辨率（跟随屏幕，最高 4K）、帧率 30–120、码率 1–60Mbps、编码器选择、悬浮球外观。

### 1.2 工程质量评估（基于源码阅读）

- 分层清晰：`capture`（投影与编码）、`buffer`（环形缓冲与保存）、`service`（前台服务）、`overlay`（悬浮球）、`ui`（Compose 界面）、`data`（DataStore 设置 + 视频库）。
- 核心逻辑（环形缓冲、PTS 重定基、ClipWriter）**有单元测试**。
- 边界情况处理细致：编码停滞看门狗自动恢复、低电量/低内存自动降码率、屏幕旋转重建悬浮窗、Android 14+ 前台服务权限适配、保存时快照与写入并行不阻塞缓冲。
- **当前零网络依赖**（仅 AndroidX + Compose + DataStore + coroutines）——加上传功能时可自由选型，无历史包袱。

### 1.3 保存链路源码（需求二的接入点）

```
RecordingService.saveClip()
  → CapturePipeline.snapshot()                    // 快照当前缓冲分片（不阻塞持续录制）
  → ClipWriter.write(snapshot, ...)               // 拼接 + MediaMuxer → MediaStore 落盘
      返回 Result(uri, durationMs, sizeBytes)      // uri = MediaStore content:// Uri
  → savedEvents.tryEmit(SavedEvent(result))        // 唯一的"保存完成"事件
```

**关键结论：只需在 `ClipWriter.write()` 成功后挂一个上传队列，完全不用动录制/缓冲核心（项目里最难、测试保护最好的部分）。**

## 2. 需求一：协管巡查即时回放取证 —— 可行，非常契合

这正是环形缓冲录屏的教科书场景。

### 2.1 有利特性

1. **不会错过时机**：发现违规后晚几秒再点保存也来得及——只要违规瞬间仍在 N 秒缓冲窗口内，点一下就全在里面；还可以连续点两次保存两段证据。
2. **不打断游戏**：悬浮球全局置顶，全屏游戏内单击即存，无需切出 MC；通知栏也有保存按钮可作备选入口。
3. **性能影响被刻意压低**：硬件编码 + 为游戏让路的编码器限速策略，默认 720p 下与 MC 同跑帧率影响小。
4. **可靠性**：前台服务 + 常驻通知 + 低内存降级与提示，不会静默失效；编码停滞有看门狗自动恢复。

### 2.2 注意事项 / 待验证项

| 事项 | 说明 | 建议 |
|---|---|---|
| 平台覆盖 | 这是安卓 App，只覆盖**安卓设备（网易基岩版）巡查的协管** | PC 端协管需另配方案（OBS 回放缓冲 / NVIDIA 即时回放） |
| 取证清晰度 | 720p 下聊天栏小字/玩家头顶 ID 可能糊 | 设 **1080p / 30fps / 约 10Mbps** |
| 内存预算 | 环形缓冲体积 ≈ 码率 × 时长（10Mbps × 120s ≈ 150MB） | 回退时长 **60–120 秒**足够，不要配 300 秒满档 |
| 音频采集 | 网易 MC 若禁止内录，自动退化为无声/纯麦克风 | 发版前在目标机型实测 |
| Android 14+ 每次开始录屏需点一次系统确认 | 系统隐私要求，无法绕过；**每个巡查 session 一次**，不是每次保存一次 | 写进协管手册 |
| 续航 | 全程硬编码录屏耗电明显 | 低档画质 + 电池优化白名单（App 引导已含）+ 长班次配充电宝 |
| DRM | DRM 保护的内容会黑屏；游戏一般不受影响 | 实测确认即可 |

## 3. 需求二：保存后自动上传自建云盘 —— 可行，中等工程量

### 3.1 推荐实现方案

| 层面 | 方案 | 说明 |
|---|---|---|
| 上传调度 | **WorkManager**（新增 `androidx.work` 依赖） | 可靠后台队列：断网自动重试（指数退避）、可设仅 Wi-Fi、App 被杀任务不丢。**"防不上传"的关键：上传无需任何人操作，保存即入队** |
| 网络层 | OkHttp，通过 ContentResolver 流式读 Uri 上传 | 不整文件载入内存，90MB 片段也稳 |
| 配置 | `data/Settings` 加一段：开关、服务器地址、Token、仅 Wi-Fi、成功后是否删本地 | DataStore 已就绪，照抄现有设置项写法 |
| 触发点 | `RecordingService` 中 `ClipWriter.write()` 成功返回后，将 `result.uri` 入上传队列 | 见 1.3 代码链路 |

### 3.2 服务端方案（自建云盘，三选一）

| 方案 | 客户端成本 | 适用 |
|---|---|---|
| ① **WebDAV**（Nextcloud / Alist / 群晖） | 一个 PUT + Basic Auth，最省事 | 已有云盘、快速落地 |
| ② **MinIO / S3 兼容** | 预签名 PUT | 后续扩展性最好 |
| ③ **自写小接收端**（几十行 Go / Flask） | multipart 接收 | 可强制命名规范（`日期_协管ID_服务器.mp4`）并落库元数据；**若要做证据管理/检索，选这个** |

### 3.3 「防止协管不上传」的增强手段（成本都低）

- 上传成功**默认不删本地**双保险；或成功自动删、失败本地保留 + UI 角标提醒重试。
- 客户端计算文件 **SHA-256** 随请求上传，服务端校验落库——建立证据防篡改链，将来质疑录像被剪辑时有据可查。
- 请求元数据带协管 ID + 设备时间 + 可选手填违规玩家名，云端按日期自动归档。
- 配置做成**二维码预置分发**，协管装好即用，避免手输配错。

### 3.4 UI / 状态可见性

- 视频库条目加上传状态角标（待传 / 上传中 / 成功 / 失败重试中）。
- 通知栏上传结果反馈。管理层能一眼看出谁没传。

### 3.5 安全边界（要向管理方说明）

Token 内置在协管手机里，属「防君子」级别——协管是自己人，风险可控；服务端务必：
- 强制 HTTPS；
- 只接受带 Token 的上传；
- 限制单文件大小与频率。

## 4. 合规与维护事项（必读）

1. **GPL-3.0 协议**：修改后把 APK 分发给协管属于「分发」，需向获得者提供修改后的源码。最省心做法：fork 一份放 GitHub（可私有仓库、对协管开放访问），既合规又方便团队协作。
2. **维护策略**：个人项目，fork 后自行维护。改动尽量「外挂式」（上传模块、设置项、UI），**少碰核心录制代码**（capture/buffer），方便日后合并上游修复。

## 5. 工作量估算与推进路径

| 阶段 | 内容 | 工作量 |
|---|---|---|
| 阶段一 | clone 仓库（需 JDK 17+），`./gradlew assembleDebug` 出 APK，真机实测与 MC 同跑的帧率/内存/音频 | 约半天 |
| 阶段二 | 上传功能客户端：WorkManager 队列 + OkHttp 上传 + 设置页 + 视频库状态 UI + 测试 | 2–4 天 |
| 阶段三 | 服务端：WebDAV 直接用 / MinIO 配置 / 自写接收端 + 元数据落库 | 1–2 天 |

**总体判断：该项目选型准确，架构干净、有测试、边界处理成熟，作为取证工具底座风险很低。**
